# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Вся документация, комментарии и общение с пользователем — только на русском языке.**

## Что это

Puppet-модуль `spoo_inv` (upstream: `puppet_inventory_scripts`), который раскладывает по Linux-хостам bash-агент
инвентаризации и заводит для него cron. Репозиторий намеренно совмещает две вещи: сами скрипты сбора данных
(`files/`) и puppet-обвязку для их распространения (`manifests/`) — по отдельности они бесполезны.

Агент собирает данные о железе, ПО, ОС, IP/MAC и отправляет их POST-запросом в БД инвентаризации.

## Сборки, тестов и линтера нет

Ничего не собирается и не устанавливается. Проверка изменений — только запуск скриптов на живой Linux-машине
(разработка ведётся с Windows, локально скрипты не запускаются).

Единственная автоматическая проверка — `_test_urlencode` в [files/inventory.sh:62](files/inventory.sh:62): она
вызывается безусловно при каждом старте скрипта (строка 84) и делает `exit 1` при расхождении. То есть агент
на проде не отправит данные, если `urlencode` сломан.

Ручная проверка отдельных частей на целевом хосте:

```bash
/usr/local/etc/inventory/fn.hwjson.sh          # железо, физическая машина
/usr/local/etc/inventory/fn.hwjson.sh virtual  # железо, режим ВМ
/usr/local/etc/inventory/fn.swjson.sh          # список ПО
/usr/local/etc/inventory/inventory.sh          # весь цикл, включая отправку
```

Результат работы и ответ сервера пишутся в `$logfile` (по умолчанию `/var/log/inventory.log`);
последний отправленный body лежит в `/var/log/inventory.data`.

## Поток данных

1. `cron` (по умолчанию `*/47`) запускает `/usr/local/etc/inventory/inventory.sh` от root.
2. Скрипт подгружает `/usr/local/etc/inventory/priv.conf.sh` — файл генерируется puppet-манифестом из
   параметров класса (`apihost`, `logfile`, `virtual`, `comp_id_file`).
   Образец с описанием — [files/priv.conf.sh.sample](files/priv.conf.sh.sample).
3. Собираются `os` (lsb_release), `ip`/`mac` (`ip -o`, с длинным списком исключений виртуальных интерфейсов),
   `comp` (FQDN через `hostname -f`, либо синтетическое имя в режиме тонкого клиента).
4. `fn.hwjson.sh` и `fn.swjson.sh` вызываются по абсолютным путям и возвращают JSON-фрагменты.
5. Всё urlencode-ится, складывается в `/var/log/inventory.data` и отправляется
   `curl -X POST --data @файл` на `$apihost/web/api/comps/push`; тело ответа пишется в
   `/var/log/inventory.response`, из него забирается ID записи (см. ниже).

Данные передаются через файл, а не аргументами командной строки, — иначе при большом списке ПО получается
`argument list too long` (правка 1.1.3).

## Идентификация записи в БД (защита от клонов при переименовании)

После успешной отправки агент сохраняет ID своей записи в БД в `$comp_id_file` (по умолчанию
`/var/lib/inventory/comp.id`) и на следующих запусках передаёт его как `&id=`. Сервер тогда обновляет
именно эту запись, а не ищет её по имени, — поэтому переименование хоста не плодит дубликаты.

Серверная сторона (`arms`, `modules/api/controllers/CompsController.php::actionPush`):

* `id` читается напрямую из body-параметров, **минуя** `$loader->load()` — в модели `Comps` он не является
  safe-атрибутом, и через `load()` не проходит. Если правишь эту часть на сервере — не «упрощай» до
  `$loader->id`, оно молча перестанет работать;
* если переданного `id` в БД нет (запись удалили), сервер молча откатывается на поиск по имени и создание
  новой записи. **404 не возвращается**, поэтому агенту не нужна логика повторной отправки — он просто
  сохраняет тот ID, который вернулся в ответе;
* ответ — сериализованная модель, `id` идёт первым полем; агент парсит первое вхождение `"id":<число>`.

Выключателя у механизма нет: на старом сервере лишний `id` просто игнорируется, поведение откатывается
к поиску по имени. Единственное эксплуатационное ограничение — в золотом образе, с которого клонируются
машины, файла `comp.id` быть не должно, иначе все клоны унаследуют один ID и будут перезаписывать одну запись.

Аналог в windows-версии — `../vbs/inventory` + `../vbs/libs/lib_inventory.vbs`: там ID хранится в реестре
(`HKLM\SOFTWARE\Reviakin\Inventory\compID`), логика та же. При правках стоит сверяться, чтобы ветки
не разъезжались.

## Формат JSON — не массив

`fn.hwjson.sh` и `fn.swjson.sh` печатают **последовательность объектов, разделённых запятыми, без обрамляющих
скобок** — сервер сам оборачивает это в массив. Причём соглашения разные:

* `fn.hwjson.sh` печатает `,` на отдельной строке **перед** каждым объектом, кроме первого;
* `fn.swjson.sh` ставит `,` в конце каждой строки, а последний объект (сама ОС) идёт без запятой.

При добавлении новых типов записей это соглашение нужно соблюдать, иначе битый JSON на приёмнике.

## Цепочки fallback в определении железа

Ключевая сложность `fn.hwjson.sh` — несколько путей получения одних и тех же данных, потому что набор утилит
на поддерживаемых дистрибутивах сильно разный:

* **Ядра CPU**: `nproc --all` → `lscpu -p` → суммирование `Core Count` из `dmidecode -t 4`.
  Порядок выбран эмпирически, в комментариях зафиксированы конкретные ВМ, где второй/третий способ врал.
* **Диски**: `lshw -C disk` с разбором через [files/disks.awk](files/disks.awk) → легаси-путь
  `lsblk -dnrb` + `smartctl`. lshw стал основным в 1.1.2.
* **Память**: всегда `dmidecode -t 17`, планки с `Size: No Module Installed` отбрасываются.

Флаг `virtual` (передаётся первым аргументом в `fn.hwjson.sh`) переключает сбор с качественного на
количественный: не опрашиваются модели/серийники, диски помечаются моделью из `-v def=`, процессор
описывается строкой `virtual N cores`.

## Совместимость — главное ограничение

Проверено на CentOS 5/6/7/8, Ubuntu 16/18, Debian 9–12. Почти все странности кода — следствие этого:

* свой `urlencode` на bash, потому что `curl --data-urlencode` появился в 7.18, а в CentOS 5 стоит 7.15;
* в `urlencode` есть костыль `sed 's/%FFFFFFFFFFFFFF/%/'` — в RHEL5 `printf` трактует символ как signed char;
* awk-код должен работать в mawk (Ubuntu 16/18, Debian 9/10 — это mawk 1.3.3), а не только в gawk;
  в частности, mawk 1.3.3 **не понимает POSIX-классы** `[[:space:]]`/`[[:alpha:]]` — в регулярках `disks.awk`
  используется только `[ \t]` и явные диапазоны;
* у `ip` не используется опция `-iec` (нет в старых версиях);
* перед вызовом утилит стоят проверки `which ... >/dev/null 2>&1`;
* определяется, поддерживает ли `grep` комбинацию `-Pz`.

Не «упрощай» эти места до современного синтаксиса — они написаны так осознанно.

## Внешние зависимости puppet-манифеста

[manifests/init.pp](manifests/init.pp) ссылается на сущности из других модулей, которых в этом репозитории нет:
класс `logrotate`, define `mc_conf::hotlist`, ресурсы `File['/usr/local/etc']` и `File['/etc/logrotate.d']`.
Модуль не применяется автономно — только в составе общего puppet-окружения. Каталог модуля при деплое
должен называться `spoo_inv` (имя класса), а не так, как назван локальный рабочий каталог.

Все файлы из `files/` раскладываются в `/usr/local/etc/inventory/` цепочкой `->`; пути внутри скриптов
захардкожены (`inventory.sh` вызывает `fn.*.sh`, `fn.hwjson.sh` вызывает `disks.awk`). При добавлении
нового файла его нужно и положить в `files/`, и добавить ресурс в манифест с правильным режимом
(`0755` для исполняемых, `0644` для данных).

На хосте требуются пакеты `redhat-lsb-core` и `smartmontools`; `hostname -f` должен возвращать корректный FQDN.

## Версионирование

Версия живёт в `lib_version` в [files/inventory.sh:2](files/inventory.sh:2), отправляется на сервер в поле
`raw_version` и имеет суффикс `nix`. При изменении поведения агента:

1. поднять `lib_version`;
2. добавить строку в раздел `## History` в [README.md](README.md) (формат: `* X.Y.Znix: описание`,
   новые записи сверху; `!` в начале описания — исправление бага);
3. коммит называется просто `vX.Y.Z`.

## Известные расхождения

* Режим тонкого клиента в [files/inventory.sh:141](files/inventory.sh:141) читает переменные `thinstation`,
  `thindomain`, `thinhostname`, но `$config` в манифесте их не генерирует — задать их можно только правкой
  `priv.conf.sh` вручную.
* В [files/disks.awk](files/disks.awk) размер с нераспознанными единицами (или вовсе без них — голое число
  байт) уходит на сервер числом «как есть», без пересчёта в GiB.
